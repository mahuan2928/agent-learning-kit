Case 01 · 踩坑复盘

一个简单的汇总问题，为什么跑了 5 分钟

一句话

agent 慢，很少是因为某一步慢，通常是步数太多。每多一步就多一次完整的模型往返，所以优化的对象是轮数，不是单步耗时。

真实案例

某企业 Agent 产品的试用。对多维表格里的销售明细提问：上周各店销售额从高到低排成表，并附前周比。

结果

4 分 48 秒时还没出答案，可见 36 步以上工具调用，平均每步约 8 秒。

理想路径

3～4 轮：读 skill 和 schema、两周聚合、回表。约 30 秒。

依据

只根据界面截图统计，步骤标签被截断，数字是近似值。内部实现看不到。

36 步花在了哪里

阶段步数看到的行为病根
定位数据约 13数据表 skill 连读 5 次；同一条 schema 查询命令跑 3 次上下文管理
聚合失败后换路约 12自述聚合功能持续报错，改走 字段列表 → 查询 → 表信息 → 记录列表，全量拉取工具设计
生成文件11+写文件、跑 python、读表格 skill 4 次、读校验 skill、查文件导入命令的帮助任务边界
全程—互不依赖的读操作也是一步一轮没有并行

36 步里约 18 步是读 skill 文档。只有一件事做对了：它发现有一条疑似重复的大额记录，并说要在结果里加注意书。

五条教训

教训 1 · 上下文：读过的东西不该再读

同一份 skill 读 8 次、同一条 schema 命令跑 3 次，说明前面的结果后来看不到了。原因只有两种：上下文裁剪把它裁掉了，或者 skill 拆得太碎、常用写法放在子文档里。

做法：skill 分三层，名字和描述常驻，正文触发时加载一次，冷门细节放子文档。高频用法（按日期筛选 + 分组求和）必须写在正文里。正文放进 system 并加 cache_control，常驻的成本很低。上下文压缩时，skill 正文和 schema 要列为不可裁剪。

教训 2 · 工具设计：报错要能让模型一次改对

聚合工具报错后它重试了几次都没改对，最后放弃，退化成全量拉取。这一条损失了约 12 步。

做法：报错信息写清楚哪个参数错、正确写法是什么，最好带一个可以直接照抄的示例。再提供一个高层工具，比如「表、分组字段、指标、日期范围 → 聚合结果」，一次调用完成，不要让模型自己拼 schema → field-list → query 这条链。工具的粒度应该按任务来切，而不是按 API 来切。

教训 3 · 并行：没有依赖就同一轮发

读 skill、拉 schema、查字段互不依赖，却是一步一轮。

做法：system prompt 里明确要求「互不依赖的调用在同一轮一起发」，运行框架支持一轮多个 tool_use 并发执行（本页 lib.ts 的 toolLoop 就是用 Promise.all 跑同一轮的所有调用）。两周的聚合查询也应该同一轮发。

教训 4 · 退化路径：要退就一段脚本做完

聚合真的不可用时，它是拉记录、写文件、跑 python、再检查，每一步都过一次模型。

做法：让模型写一段脚本，拉数据、筛两周、分组、算前周比、打印结果全在脚本里，中间数据不经过模型。这样退化也只多 1 轮。中间数据不进上下文，还顺便省了 token。

教训 5 · 任务边界：问什么答什么，校验力度跟风险匹配

用户只要「表でまとめて」，它却在生成电子表格文件并走校验流程，后段 11 步以上基本都花在这里。

做法：默认在聊天里直接回表格，用户明确要文件时才生成。校验按风险分级：写入、对外发送、改生产数据要校验；只读的汇总不需要。这和 P5 一样，Evaluator 只该用在「有清楚的验收标准，而且出错代价高」的地方。

改完应该长什么样

轮 1同时读 skill + 拉 schema→轮 2两周聚合同时发→前周比代码算→轮 3聊天回表 + 注意书聚合不可用 →一段脚本拉取 + 计算只多 1 轮
模型调用代码（规则 / 校验 / 计算）交给人

3～4 轮，按每轮 8 秒算约 30 秒，对比原来的 36 步、近 5 分钟。

自己做 agent 时的自查清单

检查项怎么看
同一份文档或同一条命令有没有被调用两次以上trace 里按工具名 + 参数分组计数
同一轮里是不是只有一个 tool_use看每轮 tool_use 个数，长期为 1 就是没并行
工具报错后，下一次调用有没有改对统计「报错 → 同一工具再次报错」的连续次数
中间数据有没有被整段塞回上下文看每轮输入 token 的增长曲线
输出形态是不是用户要的评测集里放几条「只要一个表」的简单问题，测轮数上限

第一列的五项都能从 trace 里自动算出来。把「轮数」和「重复调用数」放进评测指标，比只看答案对不对更早发现这类问题。

面试怎么讲

30 秒版：我测过一个企业 agent，问一个周销售汇总跑了 5 分钟。拆开看单步只要 8 秒，问题是 36 步，一半在重复读 skill 文档，另外是聚合工具报错后退化成全量拉取，还有它生成了用户没要的文件。我的改法是：skill 正文常驻并缓存，工具报错带正确示例并提供任务级的聚合工具，无依赖调用并行，退化时用一段脚本做完，默认只回聊天。理想路径是 3～4 轮、30 秒左右。

agent 慢，你第一步看什么？
先看轮数，不看单步耗时。把 trace 按工具名分组，找重复调用和长期单 tool_use 的轮次。大部分慢都是步数问题，换更快的模型解决不了。
上下文压缩会带来什么问题？
压掉了模型后面还要用的东西，它就会重新去取，等于用延迟换 token。压缩策略要区分「可丢的历史」和「必须常驻的规则和 schema」，后者不能压。
工具怎么设计才能减少步数？
按任务切粒度，而不是一个 API 一个工具。报错信息要能让模型一次改对。读类工具支持批量参数，一次查多个对象。
什么时候该加校验步骤？
按风险分级。写入、对外发送、不可逆操作要校验；只读汇总不需要。校验本身也是步数，不分级地加校验会把简单任务拖慢。

Agent Design Patterns: A Beginner’s Guide

The six most common design patterns, all explained through a restaurant kitchen. You don’t need to code, and you don’t need to know what an agent is yet. At the end there’s a short quiz: we give you a business scenario, and you pick the pattern that fits.

01 · Three things to tell apart

A single call, a workflow, an agent

A single call

You ask a cook for one dish. You say exactly what you want, and they bring it out.

Workflow

The kitchen has a set routine: prep, cook, plate, check. The manager sets the routine; each cook only handles a few of the steps.

Agent

You hand a cook a budget and let them decide for themselves what to buy, what to cook and how many dishes to make, until the job is done.

Of the six patterns on this page, the first five are all workflows: the steps are written into the program, and the model only handles the steps that need to “understand language.” In real work, a workflow is enough for most needs. It’s cheaper, the results are more consistent, and when something goes wrong you know which step broke. The part where the model makes its own decisions (the agent part) should be as rare and as small as possible.

02 · The whole idea in one line

What goes to the model, and what goes to code

Every design pattern answers the same question: once you break a job into steps, who should do each step?

Give it to the model (it understands language)

  • Classify: is this message a complaint or a booking?
  • Organize: turn handwritten notes into key points
  • Write: draft a reply, draft a proposal
  • Judge: is the tone of this reply right?

Give it to code (rules and math)

  • Check the length and look for banned words
  • Add up sales, work out growth rates
  • Check whether someone has permission
  • Decide how many retries are allowed and when to stop

Rule of thumb: if you can write it as a rule, give it to code. Code doesn’t make mistakes, costs nothing to run, and gives the same result every time. The model only does the parts you can’t write rules for. In each pattern’s flow below, blue is the model, dashed orange is code, and green is a hand-off to a person.

03 · Six patterns

One kitchen metaphor for each pattern

Pattern 1

Assembly line

Prompt Chaining

In the kitchen: Prep → cook → plate, and every step gets a quick check before it moves on. If prep finds the main ingredient is missing, the line stops. Nobody pushes ahead and cooks anyway.

Model: organize→Code: check→Model: write→Code: check
Real example
Turn handwritten notes from a customer meeting into key points. Check that the basics (number of stores, the customer’s problems) are all there. Only then draft the proposal outline, and check the draft for internal jargon.
Good for
Fixed steps, where every step can be checked.
Not for
Cases where the steps depend on the situation (use Pattern 4).
Pattern 2

Sorting the orders

Routing

In the kitchen: The front desk sorts each order as it comes in: drinks go to the bar, hot dishes go to the kitchen, complaints go straight to the manager. The person sorting doesn’t need to cook. They just need to sort fast and sort right.

A new message→A cheap model sorts it→FAQ → auto-replyComplaint → draft for a person to reviewUrgent → straight to a person
Real example
Customer messages for a restaurant chain. Booking changes and receipt requests get an auto-reply. Complaints get a draft reply for the store manager to approve. Health issues like “my stomach hurt after eating” are never left to the model: a keyword rule sends them straight to a person.
Good for
Incoming items that vary a lot, where each type is handled differently.
Not for
Cases where everything is really handled the same way.
Pattern 3

Split the work / Take a vote

Parallelization

In the kitchen: Split the work: before a dish goes out, three people check it at the same time. One checks the portion, one the temperature, one the plating. Take a vote: if you’re unsure about a new dish, three people taste it separately, and it only goes on the menu if most of them like it.

One draft→Check the numbersCheck the politenessCheck it’s fit for the customer→Combine the results
Real example
Check a draft proposal from three angles at once. Or, to decide whether a message is trying to trick the system into revealing information, ask three times and go with the majority; if the answers disagree, hand it to a person.
Good for
Angles that don’t depend on each other, or a judgment that isn’t reliable enough from one try.
Not for
Angles that must happen in order (use Pattern 1).
Pattern 4

The head chef hands out jobs

Orchestrator-Workers

In the kitchen: The head chef looks at today’s orders and decides on the spot how many helpers to use and who does what. Everyone works on their own part, and at the end the head chef puts it all together on the plate. Lots of orders today, more helpers; fewer orders, fewer helpers.

Head chef: decide how to split→Helper 1Helper 2Helper 3→Head chef: combine
Real example
A regional director asks, “Which stores had problems this week?” The main model looks at which stores have data and decides how many groups to check. Each helper uses code to crunch the numbers, and everything is combined into one report.
Good for
When you can’t know how many parts there are, or what each part is, until you see the material.
Not for
When the split is fixed in advance (use Pattern 3; it’s cheaper).
Pattern 5

Taste and improve

Evaluator-Optimizer

In the kitchen: Once a dish is ready, someone else tastes it against a standard and points out problems: too salty, gone cold, messy plating. The cook fixes it based on the feedback, three tries at most. If it still isn’t right, someone else takes over.

Model: write→Code: check length, etc.→A second model: score it→Pass → use it　Fail → rewrite with the feedback, up to 3 times
Real example
Replying to a bad Google review. First, code checks the length and makes sure no staff names appear. Then a second model scores it: does it apologize? Does it make excuses? If it fails, rewrite.
Good for
When “good enough” can be clearly defined, and a revision really does make it better.
Not for
When the standard is vague, or the first try is already good enough.
Pattern 6

Look it up in the recipe book

Agentic RAG

In the kitchen: When a cook meets a dish they don’t know, they look it up in the recipe book themselves. If the first search finds nothing, they try different words. When they’re done, they tell you which page they followed. If the recipe isn’t in the book, they say so instead of making something up.

Question→Model: decide what to search for→Code: search the documents→Model: nothing found? try other words→Answer + source
Real example
Answering a customer’s security questionnaire from the company’s security documents. The customer writes “BCP,” but the documents say 事業継続 (Japanese for “business continuity”), so the model rephrases and searches again. For how this works under the hood, see RAG: A Beginner’s Guide.
Good for
The answer is in the documents, but the question uses different words than the documents do.
Not for
Small sets of documents that you can simply hand to the model in full.

05 · Putting them together

Real systems rarely use just one pattern

Take a customer inquiry system, for example:

  1. First, sort the orders (Pattern 2): split bookings, complaints and urgent issues.
  2. For questions about bookings and policies, look it up in the recipe book (Pattern 6): find the answer in company documents and cite the source.
  3. For replies going to customers, taste and improve (Pattern 5): check the tone, the length and any mistakes, and rewrite if it fails.

In an interview, talking about combinations is far more convincing than reciting definitions one by one: it shows you know which part of the problem each pattern solves.

06 · Mini glossary

Terms you’ll meet on the hands-on page

TermIn one sentence
WorkflowThe program decides the steps; the model only does some of them
AgentThe model decides for itself what to do next and when it’s done
ToolSomething the model can ask the program to do for it, like searching documents, reading a file or doing math
Structured outputHaving the model answer in a fixed format (like a JSON table), so the program can read and check it directly
GateA check between two steps; if it fails, the work doesn’t move on
JudgeA model call whose only job is scoring, kept separate from the call that does the writing
Fan-outSending out many helpers to work at the same time; always set a limit
TraceA record of which model each step used and how much money and time it took, for comparing and debugging
Prompt injectionSomeone writes “ignore your previous instructions” in the input to make the model misbehave; treat outside input as data, never as instructions

A beginner-level interview answer

“Which agent design patterns do you know?” There are six common ones: the assembly line, sorting (routing), splitting the work and voting, the head chef handing out jobs, taste-and-improve, and question answering with search. What they have in common is that they break a job into steps, give the rules and math to code, and give the language-understanding parts to the model. I always start by asking whether a single call can do the job; if it can, I don’t use a pattern at all. If the steps are fixed, I use a workflow. Only the parts whose steps can’t be written down in advance are left to the model to decide, and I always use code to put limits on it.

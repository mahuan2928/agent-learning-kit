Agent 设计模式入门

六个最常用的设计模式，全部用餐厅厨房来讲。不需要会写代码，也不需要先懂 agent。最后有一个小测验：给你一个业务场景，你来选该用哪个模式。

01 · 先分清三件事

一次调用、工作流、agent

一次调用

请一位厨师做一道菜。你说清楚要什么，他做完端上来。

工作流（workflow）

厨房有固定流程：备料、炒、摆盘、检查。流程是店长定的，厨师只负责其中几步。

Agent

给厨师一笔钱，让他自己决定买什么、做什么、做几道，做完为止。

这一页讲的 6 个模式，前 5 个都是工作流：流程写在程序里，模型只负责其中需要「理解语言」的几步。实际工作中大部分需求用工作流就够了，它更便宜、结果更稳定，出了问题也知道是哪一步错的。真正让模型自己做决定（agent）的部分，越少越好、越小越好。

02 · 核心只有一句话

哪些交给模型，哪些交给代码

所有设计模式都在回答同一个问题：把一件工作拆开之后，每一步该谁来做。

交给模型（会理解语言）

  • 分类：这条咨询是投诉还是预约？
  • 整理：把手写记录整理成要点
  • 写作：写回复、写提案
  • 判断：这段回复语气合适吗？

交给代码（规则、计算）

  • 检查字数、有没有禁用词
  • 算销售额、算增长率
  • 判断有没有权限
  • 决定最多重试几次、什么时候停

经验法则：能写成规则的，一律交给代码。代码不会出错、不花钱、结果每次都一样。模型只做规则写不出来的部分。下面每个模式的流程图里，蓝色是模型，虚线橙色是代码，绿色是交给人。

03 · 六个模式

每个模式一个厨房比喻

模式 1

流水线

Prompt Chaining

厨房里：备料 → 炒 → 摆盘，每一步做完都检查一下再交给下一步。备料时发现缺了主料，就停下来，不会硬着头皮炒下去。

模型：整理→代码：检查→模型：写→代码：检查
真实案例
把手写的客户听取记录整理成要点，检查店铺数、课题这些前提齐不齐，齐了才写提案骨架，写完再检查有没有内部用语。
适合
步骤固定、每一步都能检查。
不适合
步骤要看情况才能定（用模式 4）。
模式 2

分单

Routing

厨房里：前台接到点单先分类：饮料给吧台，热菜给厨房，投诉直接找店长。分单的人不用会做菜，但要分得快、分得对。

新来的一条→便宜的模型分类→FAQ → 自动回复投诉 → 写草稿给人看紧急 → 直接给人
真实案例
连锁餐饮的客户咨询：预约变更、发票这类自动回复；投诉写草稿给店长确认；「吃完肚子痛」这种健康问题不交给模型判断，用关键词规则直接转人工。
适合
来的东西种类差别很大，每种的处理方式不同。
不适合
所有东西其实处理方式都一样。
模式 3

分工 / 投票

Parallelization

厨房里：分工：上菜前，三个人同时检查，一个看分量、一个看温度、一个看摆盘。投票：一道新菜拿不准，让三个人分别尝，多数说好才上。

一份草稿→检查数字检查敬语检查能否给客户看→合并结果
真实案例
提案书草稿同时从三个角度检查；判断一条咨询是不是在「套话」，问三次取多数，意见不一就交给人。
适合
几个角度互不相关，或者一次判断不够稳。
不适合
角度之间有先后依赖（用模式 1）。
模式 4

主厨派活

Orchestrator-Workers

厨房里：主厨看了今天的订单，当场决定派几个人、每人做什么；大家各做各的，最后主厨汇总装盘。今天订单多就多派人，少就少派。

主厨：决定怎么分→帮手 1帮手 2帮手 3→主厨：汇总
真实案例
本部长问「这周哪家店有问题」：主模型看了有哪些店的数据，决定分几组去查；每组的帮手用代码算数字，最后汇总成报告。
适合
要做几份、每份做什么，看了材料才知道。
不适合
分法事先就固定（用模式 3，更便宜）。
模式 5

试吃改进

Evaluator-Optimizer

厨房里：做好一道菜，另一个人按标准试吃挑毛病：咸了、凉了、摆盘乱了。厨师照着意见改，最多改三次，还不行就换人做。

模型：写→代码：检查字数等→另一个模型：打分→合格 → 用　不合格 → 带着意见重写，最多 3 次
真实案例
回复 Google 差评：先用代码检查字数、有没有写员工名字，再让另一个模型按「有没有道歉、有没有借口」打分，不合格就重写。
适合
合格标准说得清楚，而且改一次真的会更好。
不适合
标准说不清，或者第一次就够好。
模式 6

查菜谱

Agentic RAG

厨房里：厨师遇到不会的菜，自己去翻菜谱，一次没找到就换个关键词再找，做完告诉你「照第几页做的」。菜谱里没有的，就说没有，不瞎做。

问题→模型：决定搜什么→代码：搜资料→模型：没找到就换词再搜→回答 + 出处
真实案例
用公司的安全资料回答客户的安全问卷：客户写「BCP」，资料里写「事業継続」，模型自己换个说法再搜。详细原理见 RAG 入门。
适合
答案在资料里，但问法和资料的说法对不上。
不适合
资料很少，可以整份直接给模型看。

05 · 组合起来

真实系统很少只用一个模式

比如一个客户咨询系统：

  1. 先分单（模式 2）：预约类、投诉类、紧急类分开。
  2. 预约和规定类的问题，查菜谱（模式 6）：从公司资料里找答案，并注明出处。
  3. 要发给客户的回复，试吃改进（模式 5）：检查语气、字数、有没有写错，不合格就重写。

面试时用「组合」来讲，比一个个背定义更有说服力：说明你知道每个模式解决的是哪一段问题。

06 · 小词典

实战页里会遇到的词

词一句话解释
Workflow / 工作流步骤由程序决定，模型只做其中几步
Agent模型自己决定下一步做什么、什么时候结束
Tool / 工具模型可以要求程序帮它做的事，比如搜资料、读文件、算数字
结构化输出让模型按固定格式（比如 JSON 表格）回答，程序才能直接读取和检查
Gate / 关卡两步之间的一道检查，不合格就不往下走
Judge / 裁判专门负责打分的那一次模型调用，和写的那一次分开
Fan-out一下子派出很多个帮手同时干活；必须设上限
Trace / 追踪记录每一步用了哪个模型、花了多少钱和时间，用来比较和排查
Prompt injection / 提示注入有人在输入里写「忽略之前的指示」想让模型乱做事；要把外部输入当数据看

面试时的入门版回答

「你知道哪些 agent 设计模式？」常用的有六种：流水线、分单、分工和投票、主厨派活、试吃改进、带检索的问答。它们的共同点是把一件工作拆开，规则和计算交给代码，理解语言的部分交给模型。我会先问「一次调用能不能做好」，能就不用模式；步骤固定就用工作流；只有步骤事先写不出来的部分，才让模型自己决定，并且一定用代码给它设上限。

和 Harness 那篇的关系

Harness 那篇做的是自主 agent：模型自己决定下一步调什么工具、什么时候停。这一篇的前五个模式都是 workflow：控制流写在代码里，模型只负责其中几个节点。实际项目里绝大多数需求用 workflow 就够了，它更便宜、更可预测、也更好测。只有「步骤事先写不出来」的部分才值得交给自主循环（P4 的 worker、P6 的检索）。

六个模式一览

模式控制流由谁决定调用次数最常见的坑
P1 Chaining代码固定 (3–4)上一步出错，下游照单全收
P2 Routing代码 + 分类器1 + 1高风险类别交给分类器、低信心也自动处理
P3 Parallel代码N 倍合并时不去重；投票票数是偶数
P4 Orchestrator模型（拆分）不定fan-out 没上限；worker 输出被当成指令
P5 Evaluator代码（停止条件）2–6 倍没有上限的循环；裁判和生成者是同一次调用
P6 Agentic RAG模型（检索）不定编造出处；资料里没有也硬答

Pattern 01

Prompt Chaining：把一个大 prompt 拆成几个能验收的小步

一句话

步骤固定的任务，拆成几次调用，每两步之间插一道代码检查。拆的目的不是让模型「更聪明」，而是让每一步的输出都能被验收。

真实案例

走り書きのヒアリングメモ（47店舗の居酒屋チェーン、HACCP 記録が紙）→ 初回提案書の章立て。就是 lark-first-visit-pitch 前半段的骨架。

什么时候用

步骤事先确定；中间产物有明确的「合格」标准；下游步骤需要干净的输入。

什么时候别用

步骤要看情况才能定（用 P4）；一次调用就能稳定做好。

代价

调用次数 = 步数；延迟串行累加。

① 抽出Opus · low · zod→② Gate缺前提就停→③ 骨子Opus · medium→④ Check禁用词 / 店铺数 / 安全章② 不通过 →输出「次回確認事項」，停止　④ 不通过 →带着具体问题重写 1 次→仍不过 → 人改
模型调用代码（规则 / 校验 / 计算）交给人

这个案例里最重要的设计是第 ② 步：缺了前提，不让模型去猜，而是变成要问客户的问题。再看第 ③ 步：只把抽出后的结构化要件交给生成，不再给原始メモ，所以下游看到的是干净的输入。

面试怎么讲

30 秒版：Chaining 是把一个任务拆成固定的几步，每两步之间放一道代码检查。我在客户提案生成里用它：先把 hearing 记录抽成结构化要件，代码检查前提是否齐全，缺了就转成追问清单，不让模型猜；齐了才生成，生成后再用规则检查禁用词和关键数字。

为什么不一个 prompt 搞定？
一个 prompt 的输出没有中间检查点。错在第一步（比如店铺数抽错），会一路传到最后，而且很难定位。拆开之后，每步都能单独写测试、单独换模型、单独调 effort。
检查失败怎么办，会不会死循环？
重写只做一次，并且把具体问题回传给模型。第二次还不过就交给人。重试次数写在代码里，不让模型决定。
成本呢？
抽取步骤用 low effort；如果走 Gate 不通过的分支，直接省掉生成那一步。实际上比「大 prompt 失败后整个重来」更便宜。
Pattern 02

Routing：先分拣，再交给对的处理方式

一句话

先用便宜的模型给输入分类，按类别走不同的 prompt、模型和处理流程。高风险类别不靠分类器，用规则硬拦；低信心一律交给人。

真实案例

飲食チェーンの問い合わせ 8 件：予約変更、請求書、アレルギー、食中毒の疑い、接客クレーム、プロンプトインジェクション、求人、意味不明。

什么时候用

输入种类明显不同；不同类别的最佳处理（模型、prompt、是否要人）差别很大。

什么时候别用

类别之间的处理其实一样；分类本身比处理更难。

代价

每条多 1 次便宜调用；换来的是贵模型只用在需要的地方。

Pattern 03

Parallelization：分工看全，投票看稳

一句话

两种变体。Sectioning：同一份输入交给几个只看一个视角的审查员，同时跑再合并。Voting：同一个判断问几次，取多数。

真实案例

什么时候用

视角之间有依赖（用 P1）；判断本身已经很稳定，投票只是白花钱。

Pattern 05

一句话

一个调用负责生成，另一个独立调用按 rubric 评分；不合格就把具体问题回传，重写。停止条件写在代码里：全项合格，或者达到轮数上限后交给人。

什么时候用

Pattern 06

一句话

和你那份 LangGraph RAG 框架的对应

框架里的「改写 → 检索 → 重排 → 生成 → 引用核验」，在这里分别是：改写由 agent 自己做（工具描述驱动）；检索是 BM25；重排省略了（top 3 足够）；生成要求逐句标注出处；引用核验是 verifyCitations。框架里的 retry_count 循环上限，在这里就是 maxTurns: 6。换成 LangGraph 时，节点划分可以一一对应。

面试怎么讲

30 秒版：Agentic RAG 是把检索做成工具，让模型决定查几次、用什么词。适合问法和资料措辞不一致的场景。我会强调两点：一是资料里没有的必须答不知道，这在 prompt 里要求，在代码里核验；二是引用核验分「出处不存在」和「出处不是这次检索到的」两种，前者是编造，后者是凭记忆。

为什么不用向量检索？
生产里应该用混合检索（向量 + BM25）。这里用 BM25 是为了离线可测，而且它的失败模式（同义词搜不到）正好演示了为什么需要 agent 改写 query。换检索实现时只要保持 search() 的签名不变。
怎么评估 RAG 的效果？
分两层评：检索层看召回（标准答案的出处有没有出现在 top k 里）；回答层看忠实度（每句是否被出处支持）和拒答是否正确（资料里没有的有没有答不知道）。离线测试里那几条「データ保管 → 02#1」就是最小的检索评测集。
客户问「回答准不准」，你怎么说？
每句话都能点到原文；资料里没有的会明确说没有，并转给负责部门；核验不通过的回答不会直接发出。准确率用评测集的数字说话，而不是用感觉。
Case 01 · 踩坑复盘

一个简单的汇总问题，为什么跑了 5 分钟

一句话

agent 慢，很少是因为某一步慢，通常是步数太多。每多一步就多一次完整的模型往返，所以优化的对象是轮数，不是单步耗时。

真实案例

某企业 Agent 产品的试用。对多维表格里的销售明细提问：上周各店销售额从高到低排成表，并附前周比。

结果

4 分 48 秒时还没出答案，可见 36 步以上工具调用，平均每步约 8 秒。

理想路径

3～4 轮：读 skill 和 schema、两周聚合、回表。约 30 秒。

依据

只根据界面截图统计，步骤标签被截断，数字是近似值。内部实现看不到。

36 步花在了哪里

阶段步数看到的行为病根
定位数据约 13数据表 skill 连读 5 次；同一条 schema 查询命令跑 3 次上下文管理
聚合失败后换路约 12自述聚合功能持续报错，改走 字段列表 → 查询 → 表信息 → 记录列表，全量拉取工具设计
生成文件11+写文件、跑 python、读表格 skill 4 次、读校验 skill、查文件导入命令的帮助任务边界
全程—互不依赖的读操作也是一步一轮没有并行

36 步里约 18 步是读 skill 文档。只有一件事做对了：它发现有一条疑似重复的大额记录，并说要在结果里加注意书。

五条教训

教训 1 · 上下文：读过的东西不该再读

同一份 skill 读 8 次、同一条 schema 命令跑 3 次，说明前面的结果后来看不到了。原因只有两种：上下文裁剪把它裁掉了，或者 skill 拆得太碎、常用写法放在子文档里。

做法：skill 分三层，名字和描述常驻，正文触发时加载一次，冷门细节放子文档。高频用法（按日期筛选 + 分组求和）必须写在正文里。正文放进 system 并加 cache_control，常驻的成本很低。上下文压缩时，skill 正文和 schema 要列为不可裁剪。

教训 2 · 工具设计：报错要能让模型一次改对

聚合工具报错后它重试了几次都没改对，最后放弃，退化成全量拉取。这一条损失了约 12 步。

做法：报错信息写清楚哪个参数错、正确写法是什么，最好带一个可以直接照抄的示例。再提供一个高层工具，比如「表、分组字段、指标、日期范围 → 聚合结果」，一次调用完成，不要让模型自己拼 schema → field-list → query 这条链。工具的粒度应该按任务来切，而不是按 API 来切。

教训 3 · 并行：没有依赖就同一轮发

读 skill、拉 schema、查字段互不依赖，却是一步一轮。

做法：system prompt 里明确要求「互不依赖的调用在同一轮一起发」，运行框架支持一轮多个 tool_use 并发执行（本页 lib.ts 的 toolLoop 就是用 Promise.all 跑同一轮的所有调用）。两周的聚合查询也应该同一轮发。

教训 4 · 退化路径：要退就一段脚本做完

聚合真的不可用时，它是拉记录、写文件、跑 python、再检查，每一步都过一次模型。

做法：让模型写一段脚本，拉数据、筛两周、分组、算前周比、打印结果全在脚本里，中间数据不经过模型。这样退化也只多 1 轮。中间数据不进上下文，还顺便省了 token。

教训 5 · 任务边界：问什么答什么，校验力度跟风险匹配

用户只要「表でまとめて」，它却在生成电子表格文件并走校验流程，后段 11 步以上基本都花在这里。

做法：默认在聊天里直接回表格，用户明确要文件时才生成。校验按风险分级：写入、对外发送、改生产数据要校验；只读的汇总不需要。这和 P5 一样，Evaluator 只该用在「有清楚的验收标准，而且出错代价高」的地方。

模型调用代码（规则 / 校验 / 计算）交给人

3～4 轮，按每轮 8 秒算约 30 秒，对比原来的 36 步、近 5 分钟。

面试怎么讲

30 秒版：我测过一个企业 agent，问一个周销售汇总跑了 5 分钟。拆开看单步只要 8 秒，问题是 36 步，一半在重复读 skill 文档，另外是聚合工具报错后退化成全量拉取，还有它生成了用户没要的文件。我的改法是：skill 正文常驻并缓存，工具报错带正确示例并提供任务级的聚合工具，无依赖调用并行，退化时用一段脚本做完，默认只回聊天。理想路径是 3～4 轮、30 秒左右。

agent 慢，你第一步看什么？
先看轮数，不看单步耗时。把 trace 按工具名分组，找重复调用和长期单 tool_use 的轮次。大部分慢都是步数问题，换更快的模型解决不了。
上下文压缩会带来什么问题？
压掉了模型后面还要用的东西，它就会重新去取，等于用延迟换 token。压缩策略要区分「可丢的历史」和「必须常驻的规则和 schema」，后者不能压。
工具怎么设计才能减少步数？
按任务切粒度，而不是一个 API 一个工具。报错信息要能让模型一次改对。读类工具支持批量参数，一次查多个对象。
什么时候该加校验步骤？
按风险分级。写入、对外发送、不可逆操作要校验；只读汇总不需要。校验本身也是步数，不分级地加校验会把简单任务拖慢。

面试里最常被追问的五个问题

通用追问
什么时候该用 agent，什么时候用 workflow？
步骤能事先写出来就用 workflow：便宜、可预测、好测。只有「下一步做什么要看上一步的结果」而且步数不定时，才把那一段交给自主循环。即使用了 agent，也要用代码设上限（轮数、预算、工具子集）。
怎么决定哪些交给模型、哪些交给代码？
能写成确定规则的（字数、禁用词、算术、权限、出处是否存在）一律代码；需要理解语言的（分类、改写、生成、按 rubric 判断）交给模型。高风险判断就算需要理解语言，也要加规则兜底，比如 P2 的健康被害关键词。
模型怎么选？
按节点选：路由、投票、批量 worker 用 Haiku；编排、生成、裁判用 Opus。先用最强的模型把质量做出来，再在评测集上逐个节点降级，看质量掉不掉。不要一开始就为了省钱用小模型。
成本怎么控？
看每个任务的总成本，不看单次调用。手段按顺序是：缓存（免费）→ 调低 effort → 便宜模型做简单节点 → 用代码检查提前截断（P1 的 Gate、P5 的机械检查）→ 离线任务走 Batches。
怎么防 prompt injection？
外部内容一律放进标签并声明是数据；高风险动作要人确认；最关键的是最小权限：模型拿不到的数据和工具，被注入了也做不了什么。P2 的 FAQ 回复步骤只拿到 FAQ 文本，就是这个原则。
建议的学习顺序

先 npm test 和 npm run smoke，读懂每个「由代码负责」的部分。然后按 P2 → P1 → P5 → P3 → P6 → P4 的顺序真跑，从最容易看出效果的开始。每个模式都做一次「故意搞坏」，再用 trace 对比搞坏前后的调用次数和费用，把这些数字记下来，面试时就是你自己的数据。

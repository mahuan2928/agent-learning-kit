故意搞坏

把 splitSection 里「Q: + A: 两行不拆开」的条件删掉，再跑 E1。FAQ 类问题（F 系列）会开始出现「搜到了问题行，答案在下一块」的情况。切块边界决定了检索的上限，后面的重排再强也救不回被切散的答案。

面试怎么讲

30 秒版：切块我不拍脑袋定，先标一个小评测集，用 recall@k 比较几种切法。经验上按标题切、超长小节再按语义单位细分、标题作为上下文前缀，这种做法最稳；但在具体数据上要测。我在实验里看到固定 200 字会把表头和表行切开，导致表格题漏召回，加重叠可以缓解，按结构切能根治。

块大小怎么定？
看两个约束：答案通常有多长（这里一个条款 50–150 字），以及生成时能塞几块（top 5 × 300 字，对模型来说很轻松）。太大了检索不准、引用不精确；太小了会把一句话的条件和结论拆开。
contextual chunking 有用吗？
在这个语料上没有测出提升：给检索文本加上「文書名 > 見出し」前缀后，R@1 都是 76%，MRR 0.87 → 0.86。原因是这些规程的正文本身就重复了标题里的关键词。它的价值在「正文不提主题」的文档上（比如表格、「前項の場合は…」这类条款）。我保留它，主要是因为引用时要显示出处标题；要不要加进检索文本，同样用评测集决定。

这张表里有两个反直觉的结果，都是真实知识库里会遇到的：

  1. 混合检索没有超过纯向量。向量 R@5 是 97%，混合是 95%。RRF 是等权融合：BM25 排错的时候，会把向量排对的结果往下拉。在一个 50 块的小语料上，多语种 embedding 已经足够好，BM25 的增益（编号精确匹配）体现不出来，它的噪声反而体现出来了。
  2. 日语分词决定了 BM25 是帮忙还是添乱。字符 bigram 会把「どうやって」「されるの」也当成词。口语问题（「残業代ってどうやって計算されるの？」）就会去匹配同样口语化的 FAQ 行。只做一件事，去掉纯平假名的 bigram，混合检索的 R@5 就从 89% 升到 95%。正式做法是用 Sudachi / MeCab 做形态素解析，只保留内容词。

那为什么还用混合？因为语料一大，向量检索容易在编号、型号、人名、条款号这类「字面必须一致」的查询上失手（E-221 和 E-212 只差一个数字，描述又都是「通信断」），这时 BM25 是保底。这个 lab 的语料太小，没能测出这一点，所以下一步要看的是重排（第 04 章），它能把两路召回的优点都留下。

对应框架文档 权限过滤放在哪一步？先过滤还是后过滤？

不做任何过滤时，11/46 题的前 5 条结果里出现了提问者无权查看的块。比如：

对应框架文档 规程更新了，旧版要不要从索引里删？怎么让检索只返回有效版本？

三道经费题（交通费上限、申请期限、领收书），不做处理时旧版 3 题全部排在新版前面：

  • S1 前 3：D02#1 D03#1 D02#2
  • S2 前 3：D02#2 D03#2 D02#1
  • S3 前 3：D02#3 D03#3 D14#1

旧版本身不删：审计时要能查「当时的规定是什么」。正确的做法是保留在库里，但默认检索排除；需要查历史时显式带上参数。

为什么 grade 不用 LLM 打分？
重排分数是免费的（本地模型），而且确定、可复现，阈值能用数据定。LLM 打分要花一次调用、分数会漂。只有当分数分布真的分不开时，才值得在模糊区间里加一次 LLM 判断。

System design 题的讲法：「给连锁餐饮做一个员工问答机器人」

  1. 先问边界：资料有哪些、多少、多久更新一次；有没有权限差异；答错的代价有多大（规程问答和食品安全问答不一样）；用户在哪里问（IM、店铺平板）。
  2. 离线管线：按结构切块、带上 ACL / 版本 / 更新日元数据；增量同步；embedding 模型版本固定。
  3. 在线状态图：路由 → 改写 → 混合召回（权限前过滤、排除旧版）→ 重排 → 评分（低分时改写重搜）→ 带原生引用的生成 → 核验 → 兜底。
  4. 评测先行：先标 50 题，检索层和端到端分开评，每个组件用消融实验证明价值。
  5. 上线后：监控兜底率、平均重试次数、引用覆盖率、点踩；兜底和点踩的问题人工标注后补进评测集。

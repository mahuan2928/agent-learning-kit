守护的规则只有一条：每个 tool_use 都必须在紧接着的下一条 user 消息里有配对的 tool_result。

但只写一个 validate() 函数不够：如果 messages 还是 cli.ts 里一个谁都能 push 的数组，就没有一个固定的地方可以「每次发请求前都检查」。所以这一阶段新建 context.ts，让 ContextAssembler 成为 messages 的唯一所有者：追加只能走 appendUser / appendAssistant，发请求只能走 assemble()，而 assemble() 的第一件事就是 validate()。

为什么值得单独做一个阶段

孤儿 tool_use 的伤害是持续性的：每一轮都重发全部历史，所以第 3 轮留下的那个会跟着第 4、5、6 轮一起发出去，每轮都被拒。会话从此作废，而报错位置离成因很远。

故意搞坏（这一步最有价值）

在 buildSystem() 返回的数组里加一项：{ type: "text", text: `现在时间 ${new Date().toISOString()}` }，再跑同一个任务。

判断法则

用户说「以后都要…」「每次都得…」「绝对不能…」，答案就是 hook。写进 prompt 只能做到「大概率」：prompt 是概率性的软约束，故障率不会是 0%，只会低到让你误以为是 0%，然后在生产环境出事。

Hook runner 很小。每个 hook 是一个独立子进程，从 stdin 收 JSON、往 stdout 回 JSON，不占 context window。退出码 2 表示阻断；其他非 0 退出码会打警告（最常见的原因是忘了 chmod +x，不打警告的话 hook 会静默失效）。多个 hook 串联时，后一个能看到前一个改写过的入参：

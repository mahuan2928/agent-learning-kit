The guard has exactly one rule: every tool_use must have a matching tool_result in the immediately following user message.

But a validate() function alone isn't enough. If messages is still an array in cli.ts that anyone can push to, there's no single place to "check before every request." So this stage adds context.ts and makes ContextAssembler the sole owner of messages: appends go only through appendUser / appendAssistant, requests go only through assemble(), and the first thing assemble() does is validate().

Why this deserves its own stage

The damage from an orphaned tool_use is persistent: every turn resends the full history, so the orphan left in turn 3 goes out again with turns 4, 5, and 6, and every one of them is rejected. The session is dead from that point on, and the error surfaces far from its cause.

① Why you can't "keep the complete blocks"

The instinct is "don't waste what already arrived; stitch it into a message and keep it." First, understand why history can't be edited in place

With thinking enabled, current-generation models keep the thinking blocks in history, and each block's signature is bound to all the context that preceded it when it was produced: system, tools, and every earlier message. If the prefix doesn't match, that block and everything after it become invalid, and the request returns 400.

So the three most natural approaches all fail: clearing old tool_results, summarizing early turns while keeping recent ones, and attaching a reminder to a message and removing it next turn.

Rule of thumb

When the user says "from now on, always…", "every time, you must…", or "never…", the answer is a hook. Putting it in the prompt only gets you "most of the time": a prompt is a probabilistic soft constraint. Its failure rate is never 0%; it's just low enough to fool you into thinking it is, until something breaks in production.

The hook runner is small. Each hook is an independent subprocess that reads JSON from stdin and writes JSON to stdout, consuming none of the context window. Exit code 2 means block; any other non-zero exit code logs a warning (the most common cause is a forgotten chmod +x, and without the warning the hook would fail silently). When hooks are chained, each one sees the input as rewritten by the previous one:

Acceptance check

Break any one judgment call (delete that hint, make a tool description vague, mislabel readOnly), and the eval numbers must show a drop. If they don't, your task set is too thin or your scoring too lenient. Shore up the task set before moving on.

When to build it? Day one

You don't need a framework right away, but from day one, save a few of the real tasks you've run and label whether they went right. If you wait until you have 50 users to start collecting, you'll no longer be able to tell which behaviors were designed on purpose and which broke later.

What's still missing once you're done

These eleven stages cover M1–M3, permissions, persistence, hooks, and eval. Taking it to production still takes three more pieces, all built on what you already have:

  • Subagents: a narrow interface (pass only a prompt), a subset of tools, three caps (depth / concurrency / budget), and output sanitization. In essence, you start another runLoop and give it a fresh ContextAssembler.
  • MCP: use the official SDK and start with stdio only. Wrap MCP tools as ToolDefs in the registry with effect always set to external; the loop doesn't change.
  • Queued injection (see the end of S7): worth building before hard interrupts.
